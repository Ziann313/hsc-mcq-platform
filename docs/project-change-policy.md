# Project Change Policy

## Standing instruction

Before acting on any future feature brief, audit the active MCQ GURU implementation first. Preserve an existing working feature when it satisfies the user outcome; implement only a confirmed missing or defective requirement. Do not create duplicate pages, endpoints, schemas, flows, or client-side alternatives merely because a later brief uses different names.

## Safety and scope boundaries

New work must preserve source governance, authorised-content boundaries, server-selected immutable attempts, answer-key protection, server-side scoring, owner checks, role authorization, secure payment rules, and truthful unavailable states. A requested change must be proportionate to the verified gap; do not use a feature request to redesign unrelated screens, seed invented educational data, duplicate a protected server capability in the client, or remove active schema that supports the learning and assessment engine.

## Review protocol

For every brief, compare its requested outcome, data contract, security model, routes, and UI surface with the active code and tests. Reuse and reposition existing capability where appropriate. Record deliberate deviations when a request would expose answer keys, trust unverified client state, copy unlicensed material, claim unverified official rules, or weaken an established safeguard.
